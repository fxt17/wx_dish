# 家庭厨房：云端部署与数据保存

## 当前状态

仓库已接入云端业务代码，目标环境为 `cloud1-d1g20bvre49cb67cb`。本次没有操作真实云环境、创建线上集合、部署云函数或删除旧数据。以下配置完成后，才能在开发者工具和真机验证登录、共享及持久保存。

实现使用微信云开发的传统文档数据库，不是 PostgreSQL 环境。现有 QuickStart 示例函数和它使用的集合保持不变，不参与家庭厨房业务。

## 一、部署前准备

1. 使用有权限的小程序 AppID，在微信开发者工具中导入仓库根目录。
2. 确认小程序关联了上述云环境，且环境正常可用。
3. 检查 `miniprogram/config/cloud.js`：环境 ID、函数名 `kitchenApi`、前台同步间隔统一放在这里。
4. 若环境已有其他业务，先备份原权限配置。不要删除原集合，也不要用本项目配置覆盖其他业务的云函数/存储规则。
5. 云函数需要支持 `crypto.randomInt` 的 Node.js 运行时。选择控制台当前可用的受支持版本，部署后再做实际调用验证。

环境 ID 不是密钥；项目不需要在小程序端保存 AppSecret、云 API 密钥或管理员令牌。

## 二、建立六个数据库集合

在目标环境的数据库中，逐一创建以下空集合。**不导入示例菜谱、食材或分类。**

| 集合 | 内容 |
| --- | --- |
| `kitchen_users` | 微信身份对应的成员资料、当前厨房、加入尝试次数 |
| `kitchen_spaces` | 厨房成员、邀请码信息、当前共享业务数据及版本 |
| `kitchen_invites` | 邀请码的散列索引和有效期 |
| `kitchen_requests` | 已完成的写入请求，供网络重试去重 |
| `kitchen_orders` | 已完成菜单快照和扣料记录 |
| `kitchen_ratings` | 每个成员对已完成菜单的菜品评价记录 |

对这六个集合**分别**配置小程序客户端不可直接读写：

```json
{
  "read": false,
  "write": false
}
```

仓库的 `cloudfunctions/kitchenApi/database.rules.json` 是这份规则的参考文件，上传云函数不会自动为集合应用它。集合权限规则见[腾讯云官方说明](https://cloud.tencent.com/document/product/876/123478)。

所有业务访问都走 `kitchenApi`。函数从微信可信调用上下文获取身份，不接受客户端传来的 OpenID 作为身份凭据，并在每次读写时核对当前厨房成员关系。厨房 ID 只是定位信息，不是访问凭证。

当前查询均按文档 ID 定位，不需要额外的复合索引。请勿随意清理 `kitchen_requests`：删除记录会缩短旧请求的去重保障期。

## 三、配置图片权限

对于本项目专用环境，将云存储设为 **“仅创建者及管理员可读写”**。如果环境与其他应用共用，应先评估并设计兼容的规则，不要直接切换全环境权限。

这是为了避免不同厨房的图片变成公开资源；私有文件通过临时访问链接展示，规则切换也可能影响既有文件。参见[CloudBase 云存储权限说明](https://docs.cloudbase.net/storage/data-permission)。

本项目的图片流程：

1. 用户选中的图片先保存为本机持久文件，供未提交表单草稿使用。
2. 保存菜谱/食材时上传到 `kitchens/<厨房ID>/<用户ID>/...`。
3. 数据库保存 `cloud://` 文件 ID，不保存本机临时路径。
4. 服务端验证成员身份后，为当前厨房引用的图片签发临时链接；界面优先使用该链接。

链接请求有效期为一小时。退出厨房会阻止后续数据读取和链接签发，但已拿到的链接不能保证即时失效。创建者权限还允许上传者继续访问自己的文件；这不是“退出即销毁照片”的设计。

暂不自动删除被替换/移除的云图片或本机图片草稿，以免破坏未提交内容或历史菜单。正式使用后应制定孤立文件清理和容量管理方案。云图片可能产生存储、下载费用。

## 四、上传云函数

1. 在开发者工具中选定正确云环境。
2. 右键 `cloudfunctions/kitchenApi`，选择上传并部署，使用**云端安装依赖**的方式。
3. 确认函数名为 `kitchenApi`，入口为 `index.main`，依赖安装成功。
4. 不需要为本功能部署 `quickstartFunctions`；也不要删除或改写环境中其他函数。
5. 编译小程序，在“我的”页点击“微信登录”验证。函数依赖微信调用上下文，不应通过不带微信身份的控制台测试来判断登录功能。

如控制台提供云函数调用权限设置，可对 `kitchenApi` 添加 `invoke: "auth != null"`。**保留已有 `*` 和其他函数的规则**，仅合并这一条；云函数规则是环境级配置。具体语法见[官方云函数安全规则](https://docs.cloudbase.net/cloud-function/security-rules)。函数内部的身份及成员校验仍必须保留。

若提示云服务不可用，依次检查环境关联、六个集合是否存在、函数是否部署、依赖安装和云函数错误日志。不要为解决登录失败而开放六个集合的客户端读写。

## 五、首次使用

1. 成员 A 在“我的”页填写可选称呼并登录，创建家庭/厨房。
2. 新厨房没有任何菜谱、库存或业务分类；“全部”仅是界面筛选项。
3. 创建者复制 12 位邀请码，成员 B 登录后输入邀请码加入。
4. 在点菜和冰箱的分类管理中分别建立分类，再新增菜谱、库存。
5. 同一厨房共享菜谱、食材、分类及排序、点菜购物车、当前菜单、评价汇总、骰子规则及位置。

邀请码七天有效，创建者可更换，旧码立即失效；已加入成员不受影响。每位用户当前只能加入一个厨房，最多 30 位成员；普通成员可退出，创建者暂不能退出或转让，可正常退出登录。

## 六、保存与同步约定

### 云端是最终记录

- 页面保存、增删菜品/食材、分类保存、点菜、骰子设置均通过云函数写入；确认成功后才显示保存成功。
- 点菜数量每道最多一份，共享购物车中的选择/取消按最后接受的该项操作生效；批量清空和提交菜单会检查购物车版本。
- 提交菜单只创建用量快照，不扣库存。新增、编辑、删除食材后，服务端重新计算缺料与待消耗清单。
- 冰箱“确认菜单”在事务中检查当前有效库存、按到期先后扣减、归档菜单。相同请求重试不会再次扣库存。
- 编辑同一条菜谱、食材、分类或骰子设置时检查版本；发现旧版本不会直接覆盖其他成员的修改。
- 分类重命名同时迁移现有菜品/食材和相关随机规则；有菜品/库存引用的分类不能直接删除。
- 已完成菜单与评价明细保存在云端，但暂未提供历史列表页面。每次完成菜单后，完成时的成员可分别评价一次；下一次完成该菜会更新待评价资格。

### 前台刷新

正在显示的点菜、冰箱和详情页会接收本机保存结果。小程序前台约每 10 秒读取一次云端，切回页面及点击“立即刷新”也会同步；进入后台停止轮询。它是定时同步，不是毫秒级实时推送。

编辑页不会被轮询直接覆盖输入，保存时再核对版本。轮询目前读取整个厨房快照，并取得图片链接，需关注调用量；成员/数据量增长后应拆分集合和改进增量同步。

### 断网或回执丢失

- 先把写入请求落到本机，再发送云端。存储空间不足时，不发送无法可靠追踪的操作。
- 未收到确认时保留请求，不把结果假装保存成功；“我的”会显示待确认操作。
- 点击“重试这次保存”沿用同一请求 ID；即使第一次实际已成功，也不会重复执行。
- 未解决的操作会阻止后续写入，避免不明确的顺序覆盖。恢复网络后需在“我的”手动重试。
- 发生版本冲突时可复制内容，选择“保留为本机草稿并刷新”，对照最新数据重新编辑。不会自动合并同一字段的冲突，也不会撤销已完成的云端操作。
- 菜谱、食材、分类编辑在隐藏/离开时保存本机表单草稿。成功提交或重试后只清理对应的已提交草稿，不清理之后的新编辑。
- 本机缓存按环境、经云端验证的用户及厨房隔离。新启动需联网验证身份，验证前不展示缓存厨房数据；已验证会话同步失败时保留上次读取的数据。
- 旧版未分账户的分类、骰子缓存不自动导入共享厨房；旧缓存文件和旧云资源没有被清空。需要迁移时应另行确认导入范围。

本机草稿不是云备份：清除小程序缓存、卸载、换设备或存储失败都可能使未上传内容丢失；成功保存到云端的数据不受正常退出登录影响。

### 容量与后续工作

当前每个厨房的业务状态放在一个文档中，应用层限制 300 道菜、1000 个食材批次、100 个分类/类型、序列化状态 600000 字节。该方案面向家庭，不面向高并发餐饮系统。

还需后续完善厨房转让/解散、移除成员、历史菜单界面、孤立图片清理及完整备份/恢复流程。上线前应结合真实数据量检查权限、配额、监控及费用，并自行配置适当的云端备份。

## 七、验证

在仓库根目录执行：

```sh
npm test
```

根目录测试仅使用 Node.js 内置模块，无须安装前端依赖。目前包含 43 项本地模拟场景：共享和隔离、并发版本、缺料重算、原子扣料、回执丢失、重启恢复、草稿保留、页面绑定等。模拟数据库不代表真实云端事务引擎已验证。

本次还通过了已安装的微信开发者工具 WXML/WXSS 编译器检查。**尚未部署真实云端，也未完成双微信账号真机联调。**

部署后请至少检查：

- [ ] A 首次创建厨房时无示例数据，重新启动后原厨房及数据可恢复。
- [ ] B 加入后能看到 A 的菜谱、库存及图片；A/B 的购物车、菜单、骰子规则和位置互相同步。
- [ ] 两个厨房之间无法读写数据；退出后的成员不能继续取得原厨房的最新数据。
- [ ] 新增、修改、删除木耳库存时，共享缺料清单正确更新。
- [ ] 两人同时编辑同一条记录时，旧版本提示冲突，不覆盖较新内容。
- [ ] 提交菜单不扣库存；两端重复确认只扣一次，过期库存不能使用。
- [ ] 保存时断网或退出进程，重启后可在“我的”重试，不重复创建或扣料。
- [ ] 分类返回自动保存和显式保存均正常；分类拖拽、骰子长按/动画在真机上无回归。
- [ ] 图片权限保持私有，退出登录不删除共享数据。
